# 架构与模块边界

一次自回归生成同时要解决两个问题。引擎要记住每个请求算到了哪个位置，模型要根据已有上下文计算下一个 token 的分布。现在的代码已经能用一个可替换的执行后端跑通前一个问题。Qwen 权重加载、模型计算、KV/GDN 缓存和在线服务属于后续实现。

## 一次调用经过哪些模块

| 入口 | 输入 → 输出 | 状态归属 |
|---|---|---|
| [Engine.add_request](../myvllm/engine.py) | prompt token ID、输出上限 → 请求 ID | 引擎保存 prompt 的不可变副本，分配单调递增的 ID。外部修改原始列表不会更改排队中的输入。 |
| [plan_batch](../myvllm/scheduler.py) | 活跃请求、每轮 token 预算 → 一组 BatchItem | 调度器只读请求。每个条目给出请求 ID、本轮 token、起始逻辑位置、阶段和采样标记。 |
| [ModelRunner.execute](../myvllm/engine.py) | 整批 BatchItem → 按请求 ID 索引的采样结果 | 执行接口允许后端对 token 做批处理。测试提供确定性算术后端，未来的模型后端负责前向与采样。 |
| [Engine.step](../myvllm/engine.py) | 后端结果 → 零个或多个 TokenEvent | 引擎核对返回的请求集合，更新进度，在 EOS 或输出长度达到上限时移除请求。 |

这样划分有两个直接作用。第一，同一份批次计划可以用确定性后端检查位置、归属和终止条件，也可以交给模型做数值验证。第二，以请求 ID 关联结果，允许批次中只有部分请求需要采样。如果按返回列表的下标分配结果，未完成 prefill 的请求容易领到其他请求的 token。

## 为什么先采用同步、单阶段的批次

一次 step 内先确定批次，后端完成执行后再更新请求。这给“已经算过多少 token”提供了唯一的提交位置。每轮由最早进入且仍活跃的请求选择阶段，余下预算可以用于同阶段的其他请求。这样每项工作的输入布局明确，也便于检查 chunk 在哪一轮结束。代价是长 decode 可能推迟后来的 prefill。到达率较高时，需要用长短混合负载量化这个等待，再决定怎样调整阶段优先级。

调用方串行驱动引擎。返回空事件可能表示刚算完一个中间块，判断是否还有工作要读 `engine.has_requests`。后端若返回错误的请求集合，step 抛出异常，主机请求计数不会提前推进。有状态后端的失败恢复还要处理设备侧写入，接入缓存时应共同定义。

## 接入模型和缓存的位置

模型后端将把 BatchItem 的逻辑位置转换为位置编码、attention 元数据和 GDN 状态索引。全注意力需要历史 token 的 K/V，GDN 需要对应边界的卷积状态与递归状态。因此调度器应保留逻辑 token 位置，物理页号和状态槽交给缓存管理器。每次接入真实缓存都需要定义分配、执行成功后提交、失败处理和请求结束时释放的顺序。

以未来的前缀复用为例，同一个请求若有前 512 个 token 的 KV，却只有位置 384 的有效 GDN 快照，可从前 384 个 token 的共同边界恢复。下一步输入的零基位置是 384。恢复时若把较早的状态配上较晚的输入，形状通常依然合法，但后续 logits 会偏离完整重算。后续章节应以共享前缀分叉的实例验证这一点。

当前可运行的状态轨迹见[推理循环](engine-step.md)。后续接入模型时，首先对齐同一段 prompt 的最后位置 logits，再对齐第一次增量 decode，以区分权重加载和状态续算的问题。
